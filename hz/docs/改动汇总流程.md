# 改动怎么汇总回来

> 三个人各自写自己的阶段模块，改动怎么合到一起、谁负责合。
>
> 配套：`协作入门.md`（怎么开发）、`README.md`（状态与命令）

---

## 一、先说结论：用「源码包 + 补丁」来回传

**你们的电脑不在一起，也没有内网 GitLab 和共享盘**，所以走不了"共享仓库"。
好在代码本身很小（**源码 118 个文件，压缩后 0.4 MB**），微信直接发就行。

约定一套简单流程：

```
        欧雨欣（main 负责人）
              │  ① 发源码包（微信）
              ├──────────────►  郝兮睿 / 陈铠俐
              │                    各自本地写代码、本地 git 提交
              │  ② 回传 patch（微信）
              ◄──────────────
        ③ 欧雨欣 apply + 跑测试 + 合进 main
              │  ④ 攒一批再发新源码包
              └──────────────►  下一轮
```

**两个动作就够了：发源码包（往下发）、回传 patch（往上传）。**

---

## 二、为什么必须用 patch，不能直接发文件

队友改完之后，"把改过的文件发回来"是最直觉的做法，但它有三个真实的坑：

| 做法 | 问题 |
|---|---|
| 发整个项目压缩包 | 欧雨欣无法分辨哪些是你改的，得逐文件比对 |
| 只发改动文件、按目录打包 | **比想象中危险**：共享文件（`main.py`、`schemas.py`、`types.ts`…）你手上那份是几天前拉的，整份覆盖会把**别人这几天的改动一起抹掉**，而且不报错，直到某天发现"我的接口怎么没了" |
| 把代码贴在微信里 | 容易漏、中文引号会变形、行尾会乱 |

**patch 没有这些问题**：它只记"哪一行、从什么改成什么"，不覆盖任何别人的改动。

## 三、队友侧：怎么把自己的改动导出成 patch

### 前提：本地用 git 管起来

拿到源码包解压后，先初始化一次（**只需做一次**）：

```powershell
cd D:\work\pile-lcm
git init
git add -A
git commit -m "从欧雨欣的源码包初始化"
```

> 为什么要 git init？因为后续导出 patch、回退自己改坏的地方、
> 看"我到底改了什么"，全靠它。**不需要联网，不需要远程仓库。**

### 写完之后：导出 patch

```powershell
# 看一眼自己改了哪些文件（心里有数）
git status

# 导出全部改动为一个 patch，能保留提交信息（推荐）
git format-patch --stdout HEAD > survey-20261020.patch
```

如果你是在多个提交里分批写的，上面这条会把**从 HEAD 往后所有提交**导出 ——
所以正确做法是先确认自己的起点。更稳的写法是记下起点：

```powershell
# 初始化时记下的那个提交，就是你的起点（下面用 <起点> 代替）
git format-patch <起点> --stdout > survey-20261020.patch
```

**没有提交过也没关系**，未提交的改动也能导出：

```powershell
git add -A
git diff --cached > survey-20261020.patch
```

### 文件命名（便于欧雨欣识别）

```
<阶段>-<你的名字>-<日期>.patch
例：survey-haoxirui-20261020.patch
    construction-chenkaili-20261022.patch
```

### 一起发给欧雨欣的说明

patch 里虽然带着改动，但**加一句人话说明**能省很多来回：

```
改了 5 个文件：
  新增 backend/app/models/survey.py
  新增 backend/app/services/survey.py
  新增 backend/app/api/survey.py
  改了 backend/app/main.py（加一行 include_router）
  改了 frontend/src/router/index.ts（加一条路由）

自检已过：run_all_tests.py 全过、npm run typecheck 零错误
```

## 四、欧雨欣侧：怎么把 patch 合进来

```powershell
# 进入你自己的仓库目录（下面 <仓库> 换成你的实际路径）
cd <仓库>

# 1) 先确认工作区干净（有未提交改动先处理掉）
git status

# 2) 试应用 —— --check 只看能不能打上，不改文件
git apply --check D:\下载\survey-haoxirui-20261020.patch

# 3) 正式应用
git apply D:\下载\survey-haoxirui-20261020.patch

# 如果 patch 是 format-patch 导出的（带提交信息），用 am 更好，能保留提交历史：
git am D:\下载\survey-haoxirui-20261020.patch

# 4) 跑全套自检 —— 这一步不能省，要确认没破坏公共层
cd backend
.venv\Scripts\python.exe scripts\check_db.py
.venv\Scripts\python.exe scripts\check_demo_data.py
.venv\Scripts\python.exe scripts\run_all_tests.py
cd ..\frontend
npm run typecheck
```

**测试全过**再提交：

```powershell
git add -A
git commit -m "feat(survey): 合并郝兮睿的勘察阶段模块"
```

### 打不上怎么办

`git apply --check` 报错说明**冲突**（队友的起点太旧，或和别人的改动撞了同一行）。
这种情况占少数，处理方式：

```powershell
# 用三方合并，冲突处会留下 <<<<<<< 标记，手动解开
git apply --3way D:\下载\survey-haoxirui-20261020.patch
```

解开后 `git add` 冲突文件，跑测试，再提交。
**如果只是一两个共享文件的几行冲突，直接手工加上那几行更快** —— 不要为了 patch 干净去折腾。

## 五、共享文件怎么办（关键）

有些文件是全项目共用的，三个人都可能往里加东西：

| 文件 | 通常会加什么 |
|---|---|
| `backend/app/main.py` | 注册你的路由 |
| `backend/app/models/__init__.py` | 注册你的模型 |
| `backend/app/schemas.py` | 加你的请求 / 响应类型 |
| `frontend/src/api/types.ts` | 加你的类型定义 |
| `frontend/src/api/index.ts` | 加你的 api 对象 |
| `frontend/src/router/index.ts` | 加你的路由 |
| `frontend/src/views/ProjectDetailView.vue` | 加入口按钮 |

**对这些文件，只「追加」，不要重排、不要动别人的行。** 这样 patch 里永远只有新增行，
永远不会和别人冲突。这是让 patch 流程顺畅的**唯一最重要的纪律**。

> 反例：为了"看起来整齐"把 import 那一段重新排序 ——
> 这会让整段都变成改动，和队友的 patch 必然冲突。

## 六、发源码包的节奏

**不要每改一点就发一次。** 建议：

- **每攒到一批可用的功能**（或每周一次），欧雨欣打一个新包发出去
- 打之前确认：`git status` 干净、`run_all_tests.py` 全过

打包命令：

```powershell
# 在仓库的 backend 目录下执行；<输出目录> 换成你想放 zip 的地方
cd backend
.venv\Scripts\python.exe scripts\make_dist.py "<输出目录>"
```

产物是一个约 **0.4 MB** 的 zip，里面已经带了《【先看这个】版本说明.txt》，
队友解压就能照做。

> 想连汇报图、界面截图一起发（约 30 MB），加 `--with-preview`：
> ```powershell
> .venv\Scripts\python.exe scripts\make_dist.py "<输出目录>" --with-preview
> ```

**包里不含 `node_modules` 和 `.venv`**（合计约 250 MB）——
这两个目录换机器本来就不能直接拷，队友按说明自己装一次。

## 七、合并纪律（不管用什么方式传，这几条都要守）

### 1. 公共层文件不要自己改

| 文件 | 为什么 |
|---|---|
| `core/permissions.py` | 权限引擎（单位 × 阶段 × 责任等级三层校验） |
| `core/security.py` | 密码哈希 + JWT |
| `models/enums.py` | **责任矩阵与全部枚举**。改这里等于改全平台规则 |
| `services/documents.py` | 版本状态机四条铁律，全平台唯一实现 |
| `services/workflow.py` | 两级签认引擎 |
| `api/deps.py` | 权限断言入口 |

需要改时说一声，由欧雨欣统一改 —— 这些文件冲突了非常难合。

### 2. 一定要跑自检再回传

```powershell
cd backend
.venv\Scripts\python.exe scripts\run_all_tests.py    # 564 项应全过
cd ..\frontend
npm run typecheck                                     # 应零错误
```

**测试不过就别发**，让欧雨欣去猜"哪一步坏了"比你自己修慢十倍。

### 3. 小步回传

一天一传比攒一周好合一百倍。patch 很小（几 KB），发起来没负担。

### 4. 提交信息写清楚改了什么

```powershell
git commit -m "feat(survey): 勘察钻孔数据模型与列表接口"

# 常用前缀：
#   feat     新功能
#   fix      修 bug
#   refactor 重构（不改功能）
#   docs     只改文档
#   test     加测试
#   chore    杂项（依赖、脚本）
```

## 八、为什么不做「一人一个阶段目录就彻底不冲突」

有人会想：干脆按阶段分目录，各写各的，永不冲突。

**做不到**，因为这几处天然是共享的，谁都绕不开：

1. **数据库迁移只有一条链**。两个人各自生成迁移会搞出多个 head，必须合并。
   这也是为什么 `协作入门.md` 第四节说"迁移由一个人统一生成"。
2. **权限与状态机是公共层**，各阶段都必须调同一份实现 ——
   否则"设计说通过了、施工说没通过"就没法解释。
3. **共享文件要注册新模块**（`main.py`、`__init__.py`、`router`）。
   这些文件只有一份。

所以真正可行的不是"消灭共享"，而是：
**共享文件只追加不改行 + 迁移由一个人管 + 小步回传。**

## 九、万一搞乱了怎么回退

本地 git 就是你的安全网：

```powershell
# 丢弃某个文件的所有改动
git restore backend/app/models/survey.py

# 丢弃全部未提交改动（危险，确认后再用）
git restore .

# 看自己到底改了什么
git diff

# 回到某个提交的状态
git log --oneline          # 找到目标提交
git reset --hard <提交号>   # 危险：会丢掉之后的改动
```

**只要在动手前 `git commit` 过一次，就永远回得去。**
所以建议：**开始写新东西之前先提交一次**，哪怕只是"刚解压完"。
