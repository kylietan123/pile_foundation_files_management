## 一、先搞懂三件事

### 1.1 七个阶段不是七个系统

这是最容易搞错、也最影响开发方向的一点。

```
项目（一个工程）
 ├─ 阶段 1 前期调研   ← 各自的业务功能挂在这里
 ├─ 阶段 2 勘察
 ├─ 阶段 3 设计试桩
 ├─ 阶段 4 设计       ← 欧雨欣已完成，可作为范例
 ├─ 阶段 5 施工
 ├─ 阶段 6 验收试桩
 └─ 阶段 7 运维监测
```

- **首页是"我的项目"列表**，不是阶段列表 —— 因为一个人会同时参与多个项目
- 进入项目后才看到 7 个阶段的导航
- 所以：**你不必为"勘察阶段"单独建一套项目表**，复用 `project` + `project_member` 即可

三层结构记住就行：**项目 → 阶段 → 业务功能**。

### 1.2 平台主体是「参与单位」，不是岗位

**这是本轮最大的方向调整，务必先理解，否则会写错权限。**

权限**不是逐个配的，而是从《管理流程》责任矩阵推导出来的**：

```
RESPONSIBILITY_MATRIX[阶段][单位] = 责任等级
                ↓ 推导
主 办（**）→ 查看 下载 编辑 提交 发布 签认
相 关（*） → 查看 下载 签认 提意见
参 与（√） → 查看 下载
审 查     → 查看 下载 提意见
```

对开发的影响：

- **权限判断一律用 `principal.can(动作, 项目, 阶段)`**，
  不要写 `if user.unit_code == 'SURVEYOR'`
- **单位内不区分岗位**：勘察单位里任何人都能上传，责任靠"每次操作都记姓名+工号"落实。
  不要自己加"校核人/审核人"这类字段 —— 那正是被否掉的设计
- **阶段范围也从矩阵推导**，不需要另配
- 要看某个用户在某阶段有什么权限，用 `principal.actions_in(项目, 阶段)`

#### ⚠️ 加新阶段时，要想清楚「谁需要只读查阅我的成果」

这是最容易漏的一步，而且**漏了不会报错，只会让某个单位看不到东西**。

先例：**《管理流程》原矩阵在「勘察阶段 × 设计单位」这一格没打 √**，
但设计必须参照勘察资料 —— 不补这一格，设计人员在系统里**看不到勘察报告**，
设计输入文件库就是空的。**2026-10-13 经确认补入，定为 `PARTICIPANT`（只读）**：

```
设计单位能查阅勘察报告        ✅
设计单位承担勘察阶段责任      ❌（主办仍是勘察单位）
设计单位能上传/编辑/签认      ❌
```

**这正是 `√`（参与）与 `√*`（相关）的区别：参与 ≠ 责任。**

所以你加自己的阶段时，先回答这两个问题：

1. **谁必须能看到我的成果才能开展他的工作？**（→ 给 `PARTICIPANT`，只读）
2. **谁需要对我的成果签认或复核？**（→ 给 `RELATED`，可签意见）

比如施工阶段可能要回头查阅勘察报告；验收试桩阶段要查阅设计要求。
**把答案告诉欧雨欣，由她统一改矩阵** —— 不要自己改 `models/enums.py`（公共层）。

### 1.3 签认是两级，不是三级

```
主办单位确认（CONFIRM） → 相关单位复核（REVIEW） → 已批准 → 发布
```

模板节点用 `{PRIMARY}` / `{RELATED}` 占位，运行时按当阶段的矩阵解析成具体单位 ——
**换阶段不用改模板**。相关单位可能有多个（如设计阶段是监理 + 政府审查），
是**并列任务、各签各的**，必须全部签完才推进。

> 早期设计是"校核/审核/批准"三级，已简化。原因：主体从"人"变成"单位"后，
> 设计院内部的校对/审核属于**内部流程**，平台只需要设计单位出一个人"确认"。

## 三、分工与"不要动"的清单

### 3.1 哪些文件你可以随便改

**你自己新建的文件，随便改。** 约定：

| 层 | 你的文件 | 说明 |
|---|---|---|
| 数据模型 | `backend/app/models/<阶段>.py` | 如 `survey.py`、`construction.py` |
| 业务规则 | `backend/app/services/<阶段>.py` | **业务逻辑只写在这里** |
| 接口 | `backend/app/api/<阶段>.py` | 只做参数校验 + 调 service |
| 契约 | `backend/app/schemas.py` 里**追加**你的类 | 只追加，不改别人的 |
| 前端页面 | `frontend/src/views/<阶段>*.vue` | |
| 前端契约 | `frontend/src/api/types.ts` / `index.ts` 里**追加** | 只追加 |
| 测试 | `backend/scripts/test_<阶段>.py` | 参考 `test_issues.py` 的写法 |

### 3.2 哪些文件**不要改**（公共层，改了会影响另外两个人）

| 文件 / 目录 | 为什么不能改 |
|---|---|
| `core/permissions.py` | 权限引擎。三层模型（单位 × 阶段 × 责任等级）都在这里 |
| `core/security.py` | 纯标准库实现的密码哈希 + JWT |
| `core/database.py` / `config.py` | 数据库连接与全部配置 |
| `models/base.py` | UUID 主键、命名约定（约束必须有名字，否则迁移失败） |
| `models/enums.py` | **全局枚举 + 责任矩阵**：阶段码、单位码、责任等级、版本状态、密级… |
| `models/dict.py` | 数据字典 |
| `services/storage.py` | 文件存储：内容寻址去重、签名下载 |
| `services/documents.py` | **版本状态机四条铁律**，全平台唯一实现 |
| `services/workflow.py` | **两级签认引擎**（按单位派任务） |
| `services/ledger.py` | 文件台账与追溯（谁上传/谁签认/文件在谁手上） |
| `api/deps.py` | 依赖注入 + 权限断言入口 |
| `layouts/MainLayout.vue` | 全局顶栏 |
| `router/index.ts` | 路由表 —— **你可以在里面加自己的路由行** |
| `stores/auth.ts` | 登录态 |

> **需要改这些文件时怎么办？**
> 说一声（比如"我要给 `enums.py` 加一个枚举"），由一个人统一改。
> 这些文件单个改动都很小，冲突了非常难合并。

### 3.3 五个"复用而不是重写"的能力

这五个能力已经完整实现，**直接调，不要重新写一遍**：

| 能力 | 怎么用 | 别做 |
|---|---|---|
| **文件上传 / 版本管理** | 用 `document` + `document_version` 表，调 `/api/v1/documents/*` | 别自己建文件表 |
| **两级签认流程** | 调 `services/workflow.py` 的 `start_workflow` / `pending_tasks_of_node` / `decide` | 别自己写审批状态字段 |
| **权限判断** | 用 `api/deps.py` 的 `require_project_view` / `require_action` | 别自己写 `if user.unit_code == ...` |
| **数据字典** | 用 `dict_category` + `dict_item`，调 `/api/v1/dict/*` | 别在代码里硬编码选项 |
| **文件台账与追溯** | 调 `/api/v1/projects/{id}/ledger`（`services/ledger.py`） | 别自己查版本表拼"谁上传的" |

**最后一条特别值得复用**：台账已经把"主办单位是谁、谁上传的、现在卡在哪个单位"
都算好了。你的阶段页面要展示文件清单时，直接用它比重新查表更省事，
而且**口径和全平台一致** —— 不会出现"你的页面说在等监理、台账说在等业主"。

**统一 ID 原则**：字典项、成果类型、检查项等公共分类，一律用 `dict_item.id` 外键引用，
不要各阶段各存一套自己的字符串。这样各方数据才能汇总对比。

## 四、加数据模型的正确姿势（**这一节最容易出冲突，务必看完**）

### 4.1 现状

- ORM 模型在 `backend/app/models/`，共 29 张表
- 迁移用 Alembic，目前只有**一个基线迁移**
  （`migrations/versions/*_initial_schema.py`，里面就是这 29 张表）
- 代码里**没有** `create_all` —— 表结构只由 Alembic 建立

### 4.2 加模型的步骤

**第 1 步：新建你自己的模型文件**

```python
# backend/app/models/survey.py
"""勘察阶段的数据模型。"""
from __future__ import annotations

from datetime import date

from sqlalchemy import Date, ForeignKey, String, Text
from sqlalchemy.orm import Mapped, mapped_column

from app.models.base import Base, IdMixin, TimestampMixin


class SurveyHole(Base, IdMixin, TimestampMixin):
    """勘察钻孔。

    继承 IdMixin 就有 32 位 UUID 主键，继承 TimestampMixin 就有
    created_at / updated_at（UTC），不用自己写。
    """

    __tablename__ = "survey_hole"          # 表名统一小写下划线

    project_id: Mapped[str] = mapped_column(
        String(32), ForeignKey("project.id", ondelete="CASCADE"), index=True
    )
    hole_no: Mapped[str] = mapped_column(String(50))        # 孔号
    depth_m: Mapped[float | None] = mapped_column()         # 孔深
    drilled_at: Mapped[date | None] = mapped_column(Date)
    remark: Mapped[str | None] = mapped_column(Text)
```

三条全局约定（`models/base.py` 顶部也写着）：

1. 主键统一 32 位 UUID hex 字符串，**不用自增整数**
2. 时间字段统一 UTC、以 `_at` 结尾
3. 业务表必须带 `project_id`；跨阶段共享的表还要能按 `stage_code` 过滤

**第 2 步：注册到 `app/models/__init__.py`**

不注册的话，Alembic 和程序都发现不了它。

**第 3 步：本地建表 —— 先不要生成迁移文件**

```powershell
# 删掉本地数据库，从迁移重建（会把队友已有的表也建好）
Remove-Item ..\pile_lcm.db -Force
.venv\Scripts\python.exe -m alembic upgrade head
.venv\Scripts\python.exe -m app.seed.seed_all --reset
```

**这时候你的新表还没建出来** —— 因为迁移文件里没有它。
所以你还需要**临时**用它建一次表：

```powershell
.venv\Scripts\python.exe -c "from app.models.base import Base; import app.models; from app.core.database import engine; Base.metadata.create_all(engine); print('已按当前 ORM 建表')"
```

> 这一步只建"缺失的表"，不动已有表，所以可以放心执行。
> 它是**开发期的临时手段**，正式的迁移文件由下面第 4 步统一生成。

**第 4 步：等代码合并后，由一个人统一生成迁移**

```powershell
# 由欧雨欣在收到 patch、应用并跑通测试之后执行（在主干代码上）
.venv\Scripts\python.exe -m alembic revision --autogenerate -m "feat: 新增勘察/施工阶段数据模型"
```

> **为什么必须等合并后**：迁移是链式的，必须基于"已经包含所有人改动"的代码生成。
> 你在自己那份代码上生成，等到 patch 合进来时就变成两个 head 了（见 4.3）。

### 4.3 为什么不让每个人各自生成迁移？

因为 **Alembic 迁移是链式**的（每个文件记着 `down_revision` 指向谁）。
如果三个人都基于同一个基线各生成一个，就会出现：

```
baseline ──┬── A 的迁移   ← head 1
           ├── B 的迁移   ← head 2
           └── C 的迁移   ← head 3
```

这叫 **multiple heads**，`alembic upgrade head` 会直接报错要你 merge。
更麻烦的是：A 生成迁移时看不到 B 的表，所以 A 的迁移里不会包含 B 的表 ——
合并后谁的迁移先跑、后跑，结果都不一样，排查起来非常痛苦。

**所以约定：三个人都不生成迁移文件，合并后由一个人生成一次。**
开发期用上面的 `create_all` 临时建表完全够用。

### 4.4 如果你已经不小心生成了迁移

两个办法：

```powershell
# 办法一：删掉自己生成的迁移文件（推荐，开发期还没上线，最干净）
Remove-Item migrations\versions\<你的迁移文件>.py

# 办法二：合并多个 head
.venv\Scripts\python.exe -m alembic merge -m "merge heads" head1 head2 head3
```

### 4.5 一定要避开的坑

| 坑 | 后果 | 正确做法 |
|---|---|---|
| 手工改数据库表结构 | 别人的库和你的不一致，代码在别人机器上跑不起来 | 只改模型，表由迁移建 |
| 约束不命名 | SQLite 下迁移直接报 `Constraint must have a name` | 用 `models/base.py` 的命名约定，别自己写 `ForeignKey` 而不给名字 |
| 用 PostgreSQL 专有类型（JSONB / ARRAY / CITEXT） | 开发期 SQLite 与生产 PG 行为不一致 | 用通用 `JSON`，见 `core/types.py` |
| 迁移文件用中文注释 | Alembic 按系统编码读 ini，Windows 下会 `UnicodeDecodeError` | 注释保持 ASCII |

## 五、加接口和页面的方式

### 5.1 后端：service 放逻辑，api 只做转发

```python
# backend/app/services/survey.py —— 业务规则写这里
def list_holes(db: Session, project_id: str) -> list[SurveyHole]:
    return list(db.execute(
        select(SurveyHole).where(SurveyHole.project_id == project_id)
        .order_by(SurveyHole.hole_no)
    ).scalars().all())
```

```python
# backend/app/api/survey.py —— 只做权限校验 + 调 service
from fastapi import APIRouter

from app.api.deps import CurrentPrincipal, DbSession, require_project_view
from app.schemas import ApiResponse
from app.services import survey as svc

router = APIRouter(prefix="/projects/{project_id}/survey-holes", tags=["勘察"])


@router.get("", response_model=ApiResponse[list[dict]], summary="钻孔列表")
def list_holes(project_id: str, db: DbSession, principal: CurrentPrincipal):
    require_project_view(project_id, principal)      # ← 权限入口，别省
    return ApiResponse(data=svc.list_holes(db, project_id))
```

**写操作要再断言动作权限**（`PermissionAction` 见 `models/enums.py`）：

```python
from app.api.deps import require_action
from app.models.enums import PermissionAction

require_action(principal, PermissionAction.EDIT, project_id, "SURVEY")
```

注册到 `main.py`（**加一行即可**）：

```python
app.include_router(survey.router, prefix=settings.API_PREFIX)
```

## 七、本地 Git 与回传流程

> **⚠️ 你们电脑不在一起，没有内网 GitLab / 共享盘 —— 所以没有"远程仓库"这回事。**
> 完整流程见 `docs/改动汇总流程.md`，这里给最简版本。

### 7.1 为什么还要用 git

即使不联网、没有远程仓库，本地 git 也**必须用**，因为它是三件事的唯一手段：

1. **导出 patch** —— 把改动精确地发给欧雨欣（比发改动文件安全得多）
2. **回退** —— 改坏了自己能退回去，不用重新解压
3. **看清楚自己改了什么** —— `git diff` 一目了然

### 7.2 第一次：解压后初始化

```powershell
# 解压源码包到一个纯英文、无空格的路径（中文+空格容易出各种怪问题）
# 下面 <你的仓库目录> 换成实际路径，例如 D:\work\pile-lcm
cd <你的仓库目录>

git init
git add -A
git commit -m "从欧雨欣的源码包初始化"
```

**记下这个提交号**，它是你后续导出 patch 的起点：

```powershell
git log --oneline
# 例如输出：a1b2c3d 从欧雨欣的源码包初始化
#            ^^^^^^^ 这就是你的起点
```

### 7.3 日常：小步提交

```powershell
# 看一眼改了哪些文件
git status

# 提交（信息写清楚，前缀见下）
git add -A
git commit -m "feat(survey): 勘察钻孔数据模型与列表接口"
```

提交信息前缀约定：

```
feat     新功能          fix      修 bug
refactor 重构（不改功能）  docs     只改文档
test     加测试          chore    杂项（依赖、脚本）
```

### 7.4 写完：导出 patch 发回来

```powershell
# <起点> 换成 7.2 记下的那个提交号
git format-patch <起点> --stdout > survey-haoxirui-20261020.patch
```

**没提交过也能导**：

```powershell
git add -A
git diff --cached > survey-haoxirui-20261020.patch
```

然后把 `.patch` 文件（通常只有几 KB ~ 几十 KB）微信发给欧雨欣，
**并附一句改了什么的说明**。

### 7.5 减少冲突的三条约定

1. **共享文件只追加**：`schemas.py`、`types.ts`、`api/index.ts`、`router/index.ts`、
   `main.py`、`models/__init__.py` —— 只加你的行，**不要重排、不要动别人的行**。
   这是让 patch 永远打得上的**唯一最重要纪律**。
2. **动手前先提交**：这样随时能回到已知可用的状态。
3. **一天一传**：patch 很小，小步回传比攒一周好合一百倍。

### 7.6 提交前自检（必做）

```powershell
.venv\Scripts\python.exe scripts\check_db.py          # 模型与数据库是否一致
.venv\Scripts\python.exe scripts\check_demo_data.py   # 演示数据是否自洽
.venv\Scripts\python.exe scripts\run_all_tests.py     # 564 项是否都过

cd ..\frontend
npm run typecheck                                      # 前端类型是否零错误
```

**测试不过就别发。** 让欧雨欣去猜"哪一步坏了"，比你自己修慢十倍。

### 7.7 改坏了怎么回退

```powershell
git restore backend/app/models/survey.py   # 丢弃某个文件的改动
git diff                                    # 看自己到底改了什么
git log --oneline                           # 找目标提交
git reset --hard <提交号>                    # 危险：会丢掉之后的改动
```
